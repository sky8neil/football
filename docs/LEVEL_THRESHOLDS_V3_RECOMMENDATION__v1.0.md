## 1. 设计原则

1. **一个能力指标**：收缩场均分 s。它同时覆盖胜平负与精确比分（`3w + 9e`，与 A §9.2 计分 0/3/12 代数一致），不再单设准确率或精确率门槛。
2. **一个参与指标**：累计积分（B 线）。只能挡升级，永远不导致降级。
3. **慢变量**：等级按周评估、一次一级、降级滞后，避免「每场都在跳帽子」。
4. **确定性**：同一账本、同一规则版本，任何时候回放都得到同一等级轨迹（保住 A §0.5「缓存可重建、账本是事实」这一底线）。
5. **整数真相**：所有阈值比较用整数交叉乘法；显示值只做显示（沿用 A §16.3 / §17.2 精神）。
6. **少即是多**：未上线 ⇒ 不做迁移、不做兼容字段、不做规则版本切换记录；不引入可由已有字段推导的新字段。

### 3.3 数值合理性核验（供规范附录）

期望意义下，真实场均 μ 的用户在窗口 n 时 `E[s] = (nμ + 68)/(n + 40)`。反解「期望刚好达线所需 μ」= `(T·(n+40) − 68)/n`：

| 线 | n=50 | n=100 | n=200 | n=300（窗口满） |
|---|---|---|---|---|
| Lv3 升 1.80 | 1.88 | 1.84 | 1.82 | 1.813 |
| Lv4 升 1.95 | 2.15 | 2.05 | 2.00 | 1.983 |
| Lv5 升 2.15 | — | 2.33 | 2.24 | 2.210 |
| Lv6 升 2.35 | — | — | 2.48 | **2.437** |
| Lv3 保 1.70 | | | | 1.700 |
| Lv4 保 1.85 | | | | 1.870 |
| Lv5 保 2.05 | | | | 2.097 |
| Lv6 保 2.25 | | | | 2.323 |

结论（写入规范「设计说明」，非判定条款）：
- 窗口上限 300 使先验权重永远 ≥ 40/340 ≈ 11.8%，**先验不会被完全冲掉**。因此 Lv6 期望意义下需要 μ ≥ 2.437；B 表中「很强（2.40）」用户只能靠波动升到 Lv6，但升上后期望能守住（2.40 > 2.323）。这与 B 的「Lv6 只属于很强/顶尖」意图一致，**保留**。
- Lv3 保级线 1.70 恰等于先验：窗口清空（长期不活跃）时 s=1.70，Lv3 用户不会因不活跃掉回 Lv2，Lv4+ 会逐步衰减到 Lv3。**接受**，写入说明。

## 4. 定级计算

### 4.1 有效预测与白名单

- 等级只统计「有效预测」（§2）。开赛前锁定由 A §8.4 天然保证，无需再判。
- **等级白名单 = 产品支持的全部联赛**（P §10.2 Q2：五大联赛 + 中超，无友谊赛）。配置 `LEVEL_ELIGIBLE_LEAGUES` 保留为显式枚举，当前与 `SUPPORTED_LEAGUES` 相同。
- 由于白名单 = 全集且无友谊赛，**B 值直接取 `career_points`**（§4.4）。未来若引入不计等级的赛事（杯赛、友谊赛），必须新规则版本并新增独立的等级积分口径。

### 4.2 评估窗口

对某 scope、某评估时刻 `as_of`：

1. 候选集 = 该用户满足以下全部条件的 prediction：
   - 存在 `valid_prediction_delta=1` 且 `applied_at < as_of` 的 applied item；
   - 对应 match 的 `league_id ∈ LEVEL_ELIGIBLE_LEAGUES`；
   - `match.period_anchor_at > as_of − 730 天`（24 个月定义为 **730 天**，【假设-01】）；
   - season scope 另加：`level_season_of(match.period_anchor_at) == 该赛季`（§6.1）。
2. 按 `period_anchor_at DESC, match_id ASC` 排序，取前 `min(300, 候选数)` 条为窗口。
   - 排序键用 `period_anchor_at`（与 A §7.3「周期归属只用 anchor」一致），不用结算时间、不用提交时间。
3. 每条的得分 = 该 prediction 在 `applied_at < as_of` 的 applied item 中，`source_result_version` 最大者的 `new_score`（即截至 as_of 已生效的结果）。
4. `n` = 窗口条数；`S` = 窗口得分之和（整数，0 ≤ S ≤ 12n）。

### 4.3 收缩公式与整数判定

```text
s = (S + K·μ0) / (n + K)，K = 40，μ0 = 1.70  ⇒  s = (S + 68) / (n + 40)
```

配置以整数存储：`PRIOR_WEIGHT_K = 40`，`PRIOR_MEAN_X100 = 170`，要求 `K × PRIOR_MEAN_X100` 可被 100 整除（伪分 `P0 = 68`）。

判定「s ≥ T」（T 为 ×100 整数阈值）：

```text
100 × (S + P0) >= T × (n + K)
```

- n=0 时 s = 1.70，公式无除零问题。
- 禁止先计算浮点 s 或显示值再比较；禁止持久化浮点 s 作为判断真相。
- 展示值（仅实力榜）：`s_display_x100 = floor(100 × (S + P0) / (n + K))`，输出字符串 `"x.yy"`。**向下取整**，保证「显示过线 ⇒ 真实过线」，杜绝 A §44 L96 那类「显示 60.0% 实际 <60%」的困惑。

### 4.4 B 值

| scope | B 值 |
|---|---|
| career | `career_points`（as_of 时刻的账本值：`SUM(score_delta) where applied_at < as_of`） |
| season | 该等级赛季积分（同上，按 §6.1 归属过滤） |

- **不设只增不减的独立计数器**（否决 P §10.4-2 的「建议只增不减」）。理由：B 永不导致降级，只挡升级；赛果修正使积分下降后，B 值如实下降只会让「下一次升级」晚一点，这是正确结果；另设 max 计数器会让用户凭「已被修正掉的分」升级，且多一个可漂移的缓存。
- B 值与装扮解锁读同一个 `career_points`，但两者判定独立：解锁永不回收（A §18.3），B 值随修正变动。

## 5. 评估机制（状态机）

### 5.1 每个 scope 的等级状态

```text
level_state = {
  level          int 1..6
  best_level     int 1..6，只增不减
  below_count    int 0..1     # 连续低于保级线的周评估次数
  week_base      { level, below_count, as_of }   # 本周周评估「之前」的状态，供修正重评改判
  last_inputs    { as_of, n, S, b_points, rule_version }   # 最近一次评估输入快照
}
```

career scope 挂在 `users` 上；season scope 挂在 `user_season_stats` 上（§10）。

### 5.2 周评估时刻

- `as_of` = **每周一 10:00:00（Asia/Shanghai）** = 周一 02:00:00 UTC。【需确认-01】
  - 理由：P 的「周一凌晨」会漏掉欧洲周日晚场。例：西甲周日 21:00 CET 开球 = 北京周一 04:00，完场约 05:55，按 A §42.2（完场后 10 分钟开始、15 分钟内完成）约 06:20 才结算完。10:00 留出约 3.5 小时供 Provider 延迟与重试。
  - 周一晚的欧洲比赛（北京周二凌晨）自然落入下一周评估，无需特判。
- 评估任务最早在 `as_of + 10 分钟` 启动（`LEVEL_EVAL_START_DELAY_MINUTES = 10`），给 as_of 前已开始但未提交的 item 事务留出提交时间。【假设-02】
- 数据截止**只看** `settlement_items.applied_at < as_of`，与任务实际运行时间无关 ⇒ 任务延迟、重跑、中断续跑的结果都相同；因此**不需要**像 A §34.4 那样跳过 `settling/correcting` 用户（对单个用户，每场比赛只有一个 item，要么在截止前 applied，要么不在）。
- 任务使用 job lock `sync:weekly_level_eval`（沿用 A §32.7 / §49.14 的 lease 机制）；同一 `as_of` 对同一用户同一 scope 幂等：已存在该 `as_of` 的评估结果则跳过。

### 5.3 评估对象

- career：`status=active` 且 `career_valid_predictions ≥ 1` 的用户（Lv1 用户也要评估，以便达到 20 场时升 Lv2）。
- season：当前等级赛季存在 `user_season_stats` 且用户 active。
- 已注销用户（`status=deleted`）：不再评估，等级冻结在注销时刻（A §4.5 保留历史）。
- 实现可跳过「输入与上次完全相同且 `below_count=0` 且无 24 个月过期条目」的用户，前提是结果与完整评估一致。

### 5.4 单次评估算法（纯函数）

```text
evaluate(state, inputs, cfg, as_of) -> new_state
  L  = state.level
  bc = state.below_count
  protected = as_of < cfg.PROTECTION_END_AS_OF

  # 1) 未评级
  if L == 1:
      if valid_total >= 20: return level=2, below_count=0
      else:                 return 不变

  # 2) 升级判定（一次最多一级）
  if L < 6
     and 100*(S+P0) >= PROMOTE_X100[L+1] * (n+K)
     and B >= B_POINTS[L+1]:
      return level=L+1, below_count=0

  # 3) 保级判定（Lv2 无保级线）
  if L >= 3 and 100*(S+P0) < HOLD_X100[L] * (n+K):
      if protected:           return level=L, below_count=0      # 保护期不累计
      if bc + 1 >= 2:         return level=L-1, below_count=0    # 连续第 2 次 ⇒ 降一级
      else:                   return level=L,   below_count=1
  else:
      return level=L, below_count=0                               # 回到保级线以上即清零

  # 4) 总是：best_level = max(best_level, new level)
```

规则要点（逐条写入规范）：
1. 一次评估最多升一级，最多降一级；升级优先判定（升级线必高于保级线，二者不会同时成立）。
2. 升级需 A（s 过 L+1 升级线）与 B（B 值过 L+1 的 B 线）**同时**满足；只满足其一则不升，且只要 s ≥ 当前保级线就清零降级计数。
3. 降级只看 A：连续 **2** 个周评估 s 低于**当前等级**保级线 ⇒ 降一级并清零。降级后下一周按新等级的保级线重新计数（可能继续下降，但每周最多一级）。
4. B 值下降永不导致降级。
5. Lv1、Lv2 不降级；Lv2 是已评级用户的地板（除管理员 rebuild 回放纠错外，已评级用户永不回到 Lv1）。
6. 保护期：`PROTECTION_END_AS_OF` = 首次周评估 `as_of` 起第 **13** 个周评估之后（即前 13 次周评估不降级、不累计降级计数）。【需确认-02：起点=v3 首次周评估日，由上线日决定】理由：「3 个月」按周评估计数可精确到次，避免自然月天数差异；全局一个时间点，不按用户分别计算（目的是给产品留调阈值的窗口，不是新手保护）。
7. 修正重评（§5.5）使用同一纯函数。

### 5.5 赛果修正：「改判本周结论」（supersede）

P §10.2 Q9 决策：「周一评级；随后若发生赛果修正，立即结算更新」。若把修正重评当作一次额外评估，会破坏「每周只升一级」和「连续 2 个周期」语义。本文采用**改判模型**：

1. 触发：某 correction settlement 进入 `phase=done` 后，对其中 `score_delta ≠ 0` 的 applied item 所属用户，生成修正重评任务，`as_of = settlements.settled_at`。
   - career scope：必重评。
   - season scope：仅当该比赛所属等级赛季 = 当前等级赛季时重评；已结束赛季的赛季等级冻结（§6.4）。
2. 计算：以 `week_base`（本周周评估之前的状态）为起点，用 `as_of` 时刻的最新输入重跑 `evaluate`，结果**替换**本周周评估的结论。`week_base` 不变。
3. 效果：
   - 周一因错误赛果升了级、周三修正后不再满足 ⇒ 撤回到 `week_base.level`（这不是「降级」，是纠错）；
   - 修正后满足升级条件 ⇒ 立即升一级（相对 `week_base`，本周仍最多 +1）；
   - 降级计数同理按改判结果重算，不会因修正额外 +1。
4. 保护期内：改判结果不得低于 `week_base.level`（保护期 evaluate 本身不产生降级，故天然满足）。
5. 若本周该用户尚无周评估（例如本周一时仍 < 20 场），则以当前状态为 `week_base` 执行。
6. 并发：同一用户同一 scope 的周评估与修正重评按 `as_of` 顺序串行；周评估任务未完成前产生的修正重评任务延后到周评估完成后执行。
7. 仅首次结算（非修正）**不**触发即时评估，等下周一。

### 5.6 边界与异常情形

| 情形 | 结果 |
|---|---|
| 有效预测 15 场全中 | Lv1（未评级）|
| 第 20 场有效预测在周一 10:05 applied | 本周不计入，下周一升 Lv2 |
| 一周内 20→60 场且 s 很高 | 本周最多 Lv1→Lv2，之后每周最多 +1 |
| s 在保级线与升级线之间 | 等级不变，降级计数清零 |
| s 低于保级线 1 次后回升 | 计数清零 |
| 连续 2 周低于保级线，第 2 周恰为保护期最后一周 | 保护期内不累计，保护期后需再连续 2 周 |
| 用户长期不预测 | 每周仍评估；24 个月过期导致窗口缩小，s 向 1.70 回归；Lv4+ 逐周衰减至 Lv3 为止 |
| 比赛取消 / 腰斩未结算 | 不进窗口、不计 B（无 applied item） |
| 腰斩后恢复并完场 | 按正常首次结算进入，anchor 仍为首次开赛（A §6.7） |
| 修正使 B 值跌破当前级 B 线 | 不降级；只影响下次升级 |
| 周评估任务失败/中断 | 重跑；同 as_of 幂等；结果与首次一致 |
| 规则版本在两次评估之间切换 | 下一次评估起按新版本；已产生的结论不回溯 |
| 用户注销 | 停止评估，等级冻结，不出现在当前榜单（§8.6）|

## 6. 赛季与生涯口径

### 6.1 等级赛季（替代 A 中「season_id = 联赛赛季」的等级口径）

多联赛后，五大联赛为跨年赛季（8 月–次年 5 月），中超为自然年赛季（约 3–11 月），无法共用一个联赛 `season_id` 作为「本赛季」。

- 定义 `level_season_id`，形如 `"2026_2027"`，区间为 **北京时间 7 月 1 日 00:00:00（含）至次年 7 月 1 日 00:00:00（不含）**。【需确认-03】
- 比赛归属：`level_season_of(match.period_anchor_at)`（北京时间日期判定）；**不看**联赛自身的 `season_id`。
- 例：中超 2027 赛季 3–6 月的比赛归 `2026_2027`，7–11 月的比赛归 `2027_2028`。
- `user_season_stats` 的 `season_id` 字段语义改为 `level_season_id`（字段名可保留，规范中明确语义；或改名 `level_season_id`，推荐改名以免与联赛赛季混淆）。
- 首个等级赛季：`2026_2027`（与 A 的 MVP 赛季同名，平台上线即落入该赛季）。

### 6.2 生涯等级（career）

- 窗口：§4.2，不限赛季，300 场 / 730 天。
- B 值：`career_points`，永久累计。
- 这是「对外主等级」：资料页、公开主页、榜单行内等级徽标均用生涯等级。

### 6.3 本赛季等级（season）

- 算法与生涯**完全相同**，仅数据范围限定为当前等级赛季：窗口 = 本赛季内最近 ≤300 场有效预测（730 天约束在单赛季内不起作用）；B 值 = 本赛季积分；Lv2 条件 = 本赛季有效预测 ≥ 20。
- 新赛季：用户在新赛季第 1 场有效预测正式结算时创建 `user_season_stats`，`level = best_level = 1`；**不写** level_history（from == to），因此取消 A 的 `season_start` reason。
- 用途：分享卡「本赛季等级」、等级页「本赛季」块。

### 6.4 赛季收官与冻结

- 赛季结束后的第一次周评估（as_of 在赛季结束之后）是该赛季的**最终评估**：窗口仅含归属该赛季且 `applied_at < as_of` 的预测。此后该赛季等级冻结，不再周评估、不再修正重评。
- 冻结后发生的历史赛果修正：照常更新该赛季的积分/命中统计（A §16.2），**不改**该赛季的 `level/best_level`。理由：赛季已结束，不存在「本周结论」可改判；与排行榜「is_final 后仍可改 rank」不同，等级是阶段性称号，冻结更符合用户预期。【假设-03】
- career 等级不受赛季边界影响。

### 6.5 先验 μ0 的赛季口径

- 「先验每赛季固定一次」落为：μ0 属于规则版本配置，只允许在等级赛季边界随新规则子版本变更（`level_v3.x`），生效于新版本的首次周评估；career 与 season scope 同时使用评估时生效版本的 μ0。
- `level_v3.0`：μ0 = 1.70，K = 40（P §10.2 Q8：先冻结，不等回测）。

## 7. 确定性、重建与审计

### 7.1 为什么必须处理

B 的规则是**路径依赖**的（一次一级、连续两周、保护期），当前等级不再是「当前账本的纯函数」。若不处理，A §0.5「当前等级是可重建缓存」与 §35.1 rebuild、§34.4 daily consistency 全部失效。

### 7.2 回放定义（新规范条款）

等级轨迹是以下输入的纯函数：

```text
replay(user, scope) = fold(evaluate, 初始状态 level=1,
        按 as_of 升序的事件序列：
          - 所有周评估时刻（首次周评估起的每个周一 10:00）
          - 所有影响该用户的 correction settlement 的 settled_at（修正重评）
        每个事件的输入 = 账本在该 as_of 的截面（applied_at < as_of）
        每个事件的规则 = 该 as_of 时生效的 level_rule_version 配置)
```

- 依赖的事实全部不可变：`settlement_items.applied_at`、`settlements.settled_at`、`matches.period_anchor_at`、规则版本生效表（配置，带生效 as_of，只追加）。
- 因此当前等级仍属「可重建缓存」，A §0.5 表述改为：「当前等级字段是可通过 `replay` 重建的缓存」。

### 7.3 rebuild_user_stats（替换 A §35.1 等级部分）

1. 积分/命中统计按 A §35.1 / §49.5 从 applied ledger 重建（不变）。
2. career 与各未冻结赛季的等级状态按 §7.2 回放；已冻结赛季同样回放到其最终评估为止。
3. 回放结果与缓存不同 ⇒ 覆盖缓存，并写一条 `level_history(reason=rebuild)`（允许跨多级，这是纠错）。
4. `best_level = max(现有 best_level, level_history.to_level 历史最大值, 回放轨迹最大值)`，普通 rebuild 不下降（沿用 A §35.1 语义）。
5. 管理员审计摘要（A §48.4 `rebuild_user_stats`）字段保持：`career_level`、`career_best_level`（取值域 1..6），新增 `level_state_changed: bool`。

### 7.4 daily consistency（替换 A §34.4 中 levels 项）

每日校验：
1. `last_inputs`（n、S、B）与账本在 `last_inputs.as_of` 截面的重算值一致；
2. `level/below_count` 与 `evaluate(week_base 或上一状态, last_inputs)` 一致；
3. `best_level ≥ level`，且 `best_level ≥ level_history.to_level 最大值`；
4. 可选每周一次对抽样用户做完整回放比对。

发现差异只报警，不自动修复（A §34.4 原则不变）。周中「缓存等级 ≠ 按当前账本即时计算的结果」**不是**差异。

### 7.5 level_history（替换 A §17.7 / §21.13）

- 仅当 `from_level ≠ to_level` 时写（沿用 A）；`below_count` 变化不写 history（它可由回放得出）。
- `reason` 封闭枚举：`weekly_eval` | `correction_reeval` | `rebuild`。删除 `settlement`、`correction`、`season_start`。不新增「规则版本切换」类 reason（未上线，P §10.2 Q10）。
- 修正重评撤回本周升级时，写一条 `correction_reeval`（from=改判前、to=改判后），**不删除、不改写**原 `weekly_eval` 行（A §0.6）。
- 字段见 §10.3。

## 8. 排行榜（覆盖 A §19 / §27 / §34 / §35.2 相关部分）

### 8.1 榜单总表

| 榜 | `board` | 排序主键 | 入榜门槛 | 周期 | 更新方式 | 默认 |
|---|---|---|---|---|---|---|
| 本周榜 | `week` | 本周预测分 | 本周 ≥ 1 场有效预测 | ISO 周（北京时间，A §7.1，按 anchor 归属） | 每场结算后增量重排（沿用 A §15.8 / §34.3） | ✅ |
| 生涯榜 | `career` | `career_points` | `career_valid_predictions ≥ 1` | 无 | 快照，每 60 分钟一次【假设-04】 | |
| 实力榜 | `strength` | s（预言指数） | 窗口 n ≥ **50** | 无 | 快照，每次周评估任务完成后 + 每日 1 次（吸收修正重评）【假设-05】 | |

- **取消月榜**（A §19.1 `month`、§1.2 第 24/26/28 项）。P §10.3 只列三个榜；月榜与本周榜同质且多一套聚合与封榜。【需确认-04】
- 历史周榜保留：`week` 支持 `period_key` 查询历史周，历史周 `is_final` 与修正规则沿用 A §19.7 / §32.6。
- 本周榜门槛由 A 的 3 场降为 1 场：排序主键是**总分**而非比率，不存在小样本虚高问题（P §10.3「无门槛」）。
- 准确率在所有榜单中**退出排序与展示**（P §10.3「明确避免裸胜率做榜」）。

### 8.2 排序与并列（替换 A §19.4 / `compare_ranking_entry`）

本周榜 / 生涯榜（同一比较器，字段取对应周期/生涯值）：
1. 分数 DESC
2. `exact_hits` DESC
3. 有效预测数 **ASC**（同分同精确时，用更少场次拿到同样分数者优先）
4. `last_scoring_match_at` ASC（非 null 优先于 null，A §19.5）
5. `user_id` ASC

实力榜：
1. s DESC（交叉乘法：`(S_a+P0)(n_b+K)` vs `(S_b+P0)(n_a+K)`）
2. 窗口 n DESC（样本更多者优先）
3. `user_id` ASC

说明：
- P §10.3「先达到该分的时间」定义为 `last_scoring_match_at`（最后一次得分比赛的 `period_anchor_at`），这正是累计分达到当前值的时刻；修正时重算规则沿用 A §15.7。生涯榜为此新增 `users.career_last_scoring_match_at`。
- P §10.3「避免把预测场次当排序键」理解为「不得作为主排序键」；作为第 3 并列键合规。方向取 ASC 以奖励效率、抑制刷量。【需确认-06】
- 并列规则写在榜单说明中，不在主界面（前端事项，此处仅记录）。

### 8.3 范围：全站 / 我的群

- `scope=global`：全体 active 用户。
- `scope=group&group_id=…`：仅该群成员，排序规则与全站相同，名次在群内独立计算。
- 群机制（全新，A 无对应，P §10.4-6）——最小规则集：【需确认-07：以下上限均为假设值】
  - 群是**平台自建群**，不依赖微信好友关系链（P §10.3）；由用户创建，产生 8 位邀请码（字符集 `A–Z` 与 `2–9`，去除 `O/I/0/1`），可通过「分享到群」携带邀请码加入。
  - 每群成员上限 500；每用户最多加入 20 个群、最多创建 5 个群。
  - 群名不开放自由文本（避免内容安全审核面），显示为「{群主昵称}的预言群」；群主注销后群名显示「已注销用户的预言群」，群继续存在。
  - 成员可随时退出；群主不可退出，只可解散（软删除，`status=dissolved`，A §0.6 精神）。
  - 加入/退出立即影响群榜；群榜不单独持久化，基于全站榜数据按成员过滤后排序。
  - 集合：`groups{group_id, owner_user_id, invite_code UNIQUE, status, member_count, created_at, updated_at, schema_version}`、`group_members{group_id, user_id, status(active,left), joined_at, left_at}`，唯一 `(group_id, user_id)`。

### 8.4 展示口径

- 列表：只提供前 **20** 名；分页每次 **10** 条（第 1 页 1–10，第 2 页 11–20，无第 3 页）。P §10.3「只显示前 20 + 每次 10 条下拉加载」按此统一。
- 行字段：名次、`user_id`、展示名、`favorite_team_id`、生涯等级、主排序值；本周/生涯榜另给有效预测数（只展示，P §10.3）、`exact_hits`；实力榜给 `strength_index`（`"x.yy"`，§4.3 向下取整）与窗口 n。
- 「我的名次」（固定底部，替换 A §19.8「不提供我的全局排名」）：

| 状态 `me.status` | 条件 | 展示字段 |
|---|---|---|
| `ranked` | 已入榜 | 名次 r ≤ 20 ⇒ `rank=r`；r > 20 ⇒ `rank=null`，`top_percent = clamp(ceil(100·r/N), 1, 99)`，N = 该榜（该范围）入榜总人数 |
| `not_participated` | 本周/生涯无有效预测 | 无 |
| `below_threshold` | 仅实力榜，窗口 n < 50 | `remaining_valid_predictions = 50 − n` |

  - `top_percent` 用整数：`(100·r + N − 1) div N`，再 clamp 到 [1, 99]；永不显示绝对末位、永不出现「垫底」。【假设-06：绝对名次阈值 20、clamp 上界 99】
- 顶部「更新时间」`updated_at`：本周榜 = 该周期最近一次重排完成时刻；生涯榜/实力榜 = 快照时刻。
- 未开赛（未结算）的预测不影响任何榜（天然成立：榜单只读 applied 账本）；公开主页不得返回他人**未过截止时间**比赛的预测内容（防抄作业）。
- 点击行进入对方公开主页，字段见 §11。

### 8.5 实力榜空状态文案 vs Q12（P §10.4-8 结论）

- 允许显示「再完成 X 场有效预测即可进入实力榜」，X = `max(0, 50 − 窗口 n)`。
- 等级页 Lv1 允许显示「再完成 X 场有效预测获得评级」，X = `max(0, 20 − 有效预测数)`。
- **禁止**任何基于分数差的进度（「差 0.05 分」「再拿 X 分升级」「距离下一级 X%」）。
- 理由：B 反对的是「分差进度」（诱导刷分、暴露噪声）；**场次门槛**是确定的整数条件，不暴露 s，与 Q12 本意不冲突。【需确认-08】

### 8.6 其它

- 已注销用户：不进入本周榜/生涯榜/实力榜的当前排序（重排与快照时过滤）；已 `is_final` 的历史周榜保持原样、显示「已注销用户」（A §4.5 / §44 M102）。【假设-07】
- 性能：生涯榜、实力榜 Top20 与「我的名次」必须来自快照或索引计数，不得实时全量扫描 predictions（A §42.1）。
