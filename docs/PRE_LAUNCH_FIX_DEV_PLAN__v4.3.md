## 2. 仍需处理的问题

### CR43-01（P1，来自 CR42-01）：赛果读取响应乱序时，可把 A 的比分提交给 B

- **位置**：`admin/app.js:454`（`await api.getMatch(matchId)` 后直接写表单，无请求序号与目标校验）、`admin/app.js:491`（提交使用当前输入框的 `match_id` 与表单比分）。
- **已修复部分**：顺序读取"有比分 A → 无比分 B"时，两个比分框会被清空；空比分与非法比分会被 `parseNonNegativeInteger` 拦下，不再沿用 A 的比分。
- **触发场景**：A 为 `4:1 / result_version=1`，B 为 `2:0 / result_version=1`。先读取 A，随即把 `match_id` 改为 B 并再次点击"读取比赛"；B 的响应先返回，A 的旧响应后返回。
- **实际行为与根因**：读取响应没有任何"是否仍属于当前目标"的判断，旧响应晚到会覆盖版本与比分输入框，而 `match_id` 输入框已经是 B。提交时组合成"B 的 ID + A 的比分"。两场 `result_version` 相同，`src/application/admin-result-correction.ts:180` 的版本校验无法识别串场，会按该比分写入 B。
- **验证证据**：主审执行当前 `admin/app.js` 的真实事件处理器（`rc-load-match-btn` click ×2 逆序完成 → `result-correction-form` submit），实际发出的请求体为 `{ expected_result_version: 1, regular_home_score: 4, regular_away_score: 1 }`，目标为 B 的 `match_id`。
- **影响**：与 CR42-01 同类数据串场，后续结算以错误正式赛果为依据。
- **最小修复方向**：读取环节引入递增请求序号并校验 `match_id` 仍为当前值后才写表单；提交时校验表单数据来源于当前已加载的比赛。
- **最小回归场景**：A、B 版本相同时逆序完成两次读取，最终表单必须是 B 的数据；此时提交只能提交 B 自己的比分。
- **现有测试缺口**：新增的 `admin/admin-frontend.test.mjs` 用例只覆盖顺序读取（A → B 依次完成），未覆盖响应逆序完成。

### CR43-02（P2，来自 CR42-04）：注销提交与周榜重排分离，期间对账误报且重排失败无法重试补齐

- **位置**：`src/application/profile-mutation.ts:302`（返回注销结果）、`:306`（`rebuildAffectedWeekRankings` 在注销事务之外调用）、`:339`（内部按周获取 ranking 锁）。
- **已修复部分**：无竞争的正常路径下，注销后会重排未封板周榜；`lockTrace` 已验证锁序为"注销事务提交 → 再取 ranking 锁"，不与 users 行锁交叉；每日对账在流程结束后为零差异。
- **触发场景一（中间态被对账读到）**：用户本周已有名次，注销事务提交后、周榜重排事务完成前，每日一致性任务运行并读到"用户已 `deleted`、周榜仍保留原名次"的已提交状态。固定快照无法消除该窗口，因为它完整包含一个真实的中间态。
- **触发场景二（重排被锁挡住）**：另一正常任务持有同一周 ranking 锁超过重试窗口，`rebuildGlobalRanks` 在约 350ms 重试后抛 `RANKING_REBUILD_ALREADY_RUNNING`。此时账号已注销、旧名次保留；释放锁后重试注销返回 `USER_DELETED`，不会补做重排。
- **验证证据**：主审复用新增回归用例的结算与两用户周榜数据，在注销前插入一次对账：注销前差异为 0；注销提交后、重排前出现两条 `global_rank` 差异（`actual=1/expected=null`、`actual=2/expected=1`）；重排完成后名次正确，但误报告警已持久化为 `open`。独立审查另复现了锁竞争路径：注销接口报错而账号已是 `deleted`、`global_rank` 仍为 `1`。
- **影响**：正常注销在两处产生可见不一致——运营侧收到假告警；接口报告失败但注销已生效，且无法通过重试补救。
- **最小修复方向**：让"注销状态"与"受影响周榜名次"在同一可恢复单元内提交（例如把重排纳入注销事务并沿用既有锁序，或将未完成的重排登记为可重试待办，由后续任务补齐），避免对账读到中间态，也避免注销成功而重排永久缺失。
- **最小回归场景**：① 本周结算 → 注销 → 在注销与重排之间运行对账，差异必须为 0 且不新开告警；② 预先占用周榜锁再注销，接口与名次结果必须一致（要么都成功，要么都未生效并可重试）。
- **现有测试缺口**：新增用例只在 `deleteMyProfile()` 整体返回后运行对账，未覆盖两步之间的窗口；也未覆盖周榜锁被占用时的注销结果。

### CR43-03（P1，来自 CR42-06）：独立修正补偿先执行时仍跳过漏评周

- **位置**：`src/application/weekly-level-eval.ts:85`（`anchorEvalMs` 取 `max(last_eval_as_of, week_base_as_of)`，未区分该时间来自周评估还是修正重评）、`:694`（补算以该锚点为起点）；独立补偿入口 `src/runtime/scheduled-jobs.ts:781` → `src/application/level-correction-reeval.ts:479`。
- **已修复部分**：无修正场景的逐周补算成立（漏评两周后恢复，等级与 `replayLevel` 一致，含 `level_history` 与 level_state 字段）；由周评估统一接管 pending 修正的场景也已通过（新增 `runPendingBefore` 的 `onBeforeSettlement` 回调会先补当周评估）。
- **触发场景**：漏评多周且期间存在 pending 的往周修正；独立补偿任务先于周评估恢复运行。`level-correction-reeval.ts:119` 对往周修正不再判定"周任务未完成"，因此可以先行完成重评并把 `last_eval_as_of` 推进到修正时间。
- **实际行为与根因**：新增的"修正前先补周"逻辑只接在周评估自身的 pending 处理路径上，独立补偿 `runPendingCompensation()` 不经过该回调。补偿推进锚点后，周评估以该日期作为补算起点，遗漏更早的未评估周，且该周窗口事实已被更宽的累计截面吞掉，无法自动追平。
- **验证证据**：主审亲自执行真实服务——首评 2026-08-10，漏掉 8/17、8/24，8/26 存在修正；8/31 先运行 `LevelCorrectionReevalService.runPendingCompensation()`，再运行 `WeeklyLevelEvalService.run()`。补偿返回 `completed`，锚点变为 `2026-08-26T05:00Z`，最终 `career_level=4`；同一账本 `replayLevel` 为 **5**。
- **影响**：等级与保级次数长期落后于账本回放；每日一致性校验与管理员重建会持续报等级差异，重建时等级跳变。
- **最小修复方向**：让独立补偿在推进 `last_eval_as_of` 前，同样按遗漏周逐周补算（复用周评估的补算序列定义），或在补偿前先确保该用户已补算到修正所在周期。
- **最小回归场景**：同一账本分别走"补偿先执行"和"周评估先执行"两条顺序，最终等级必须都等于 `replayLevel`。
- **现有测试缺口**：新增用例覆盖"周评估统一接管 pending 修正"，没有覆盖"独立补偿先执行、周评估后恢复"的执行顺序。

### CR43-04（P2，来自 CR42-08）：预算耗尽时游标无法保存组内进度，仍反复查询最早一批

- **位置**：`src/application/provider-stale-recovery.ts:101`（先查完全部候选日期才 `yield`）、`:120`（整组"联赛＋赛季"完成后才标记 `processedIds`）、`:126`（预算耗尽时只推进"已完整处理的连续前缀"）。
- **已修复部分**：预算充足时持久化游标生效。11 场滞留、仅第 11 场可恢复时，第一轮处理前 10 场并写入游标，第二轮（含进程重启）能访问并恢复第 11 场；队尾不足 10 场时游标回卷为空。
- **触发场景**：最早 10 场属于同一联赛赛季、分布在十个日期，单轮可用额度不足以查完这组日期。
- **实际行为与根因**：组内日期循环中途预算耗尽时，`processedIds` 尚未记录任何候选，`contiguousLast` 为空，`onCursorAdvance` 不被调用，游标保持 `null`。下一轮从队首重新查询同样日期，再次在相同位置耗尽额度。
- **验证证据**：主审连续执行三轮实际 `ProviderStaleRecoveryService.run()`，11 场滞留分布于 `2026-09-01`～`2026-09-07`，每轮额度够 6 次请求。三轮均为 `kind=completed / items_read=0`，访问日期均为 `09-01…09-07`，持久游标始终为 `null`，第 11 场从未被访问。每日额度重置后重复同一过程。
- **影响**：滞留比赛长期得不到恢复，需等每日全量同步或人工处理；旧季已退出全量探测窗口时影响持续。
- **最小修复方向**：按已尝试的候选或已查询日期保存组内进度（例如游标记录到"已尝试日期/候选"粒度，或每查完一个日期就推进可恢复的进度），使额度不足时也能在下一轮继续。
- **最小回归场景**：11 场滞留分布多日、每轮额度不足以覆盖全部日期，连续多轮后第 11 场必须被访问；游标不得停留在 `null`。
- **现有测试缺口**：新增 `[CR42-08]` 用例只覆盖"额度充足、可完整处理前 10 场"的路径，未覆盖组内预算耗尽。

### CR43-05（P2，来自 CR42-09）：服务端已排除的停用球队被静态名单回填，用户可选但无法保存

- **位置**：`miniprogram/pages/settings/settings.js:80`（`mergeServerAndRegistryTeams` 无条件遍历 `TEAM_REGISTRY` 回填未出现在服务端结果中的球队）。
- **已修复部分**：动态主队主链路已接通——设置页调用 `GET /v1/teams` → 网关路由 → 仓储 → `active` 过滤 → 搜索/选择 → 资料保存；包外升班马可以选中并保存成功。
- **触发场景**：包内已有球队在服务端为 `inactive`，`/v1/teams` 成功返回其他 active 球队。
- **实际行为与根因**：合并函数只对"服务端返回的项"按 status 过滤，对"回填的注册表项"不做任何状态校验，因此停用队仍出现在选择器。保存时 `src/application/profile-mutation.ts:213` 校验 `status === Active`，返回 `TEAM_NOT_FOUND`。
- **验证证据**：主审执行当前设置页 `loadTeams()`，服务端仅返回一支新增球队时，被停用的包内球队仍在可选项内（可见球队数 113 = 服务端 1 + 注册表回填 112）；再调用实际 `ProfileMutationService.updateMyProfile()` 保存该停用队，返回 `TEAM_NOT_FOUND`。独立审查同样得到 `PICKER_HAS_INACTIVE=true`。
- **影响**：用户能选中一个必然保存失败的选项，属于新增动态名单后仍保留的候选有效性缺口。
- **最小修复方向**：接口成功时以服务端返回的球队集合为准，静态表仅用于补展示资料；接口失败时才整体降级到静态名单。
- **最小回归场景**：服务端返回 active 集合不含某包内球队时，该球队不得出现在选择器中。
- **现有测试缺口**：`miniprogram/pages/settings/settings.test.mjs` 未覆盖"服务端成功但某包内球队为停用"的场景。

### CR43-06（P2，来自 CR42-09）：新增主队资料只缓存在设置者本机，分享接收者与公开主页无法展示

- **位置**：`miniprogram/pages/settings/settings.js:277`（保存时写入 `team_name:`/`team_logo:` 本地缓存）、`miniprogram/pages/share-card/share-card.js:67`、`miniprogram/pages/public-profile/public-profile.js:45`（均只查注册表 + 本机缓存）。
- **触发场景**：用户把包内不存在的新升班马设为主队，随后将分享卡转发给未缓存该球队的其他用户。
- **实际行为与根因**：分享数据只携带 `favorite_team_id`（`src/application/share-card.ts:435`），接收端解析名称/队徽时既没有注册表条目，也没有本机缓存，且不会调用 `/v1/teams`，因此落到兜底文案与占位队徽。
- **验证证据**：主审执行当前 `resolveFavoriteTeam()`：发送端缓存存在时得到 `{ favoriteTeamText: "升班马竞技", favoriteTeamLogo: "https://example.com/promoted.png" }`；清空缓存模拟接收端后，同一 `team_id` 得到 `{ favoriteTeamText: "已选择球队", favoriteTeamLogo: "team-placeholder.png" }`。公开主页为同构代码路径。
- **影响**：新增动态主队能力的展示链路未闭环——"换季零重发"在主队展示处仍需依赖接收端本机缓存。
- **最小修复方向**：分享卡与公开主页在注册表/缓存未命中时，按 `favorite_team_id` 从服务端球队数据解析名称与队徽（可复用 `/v1/teams` 结果）。
- **最小回归场景**：接收端无任何本地球队缓存时，打开含新升班马主队的分享卡/公开主页，必须显示该队中文名与队徽，而非"已选择球队"与占位图。
- **现有测试缺口**：分享卡与公开主页测试均在本机缓存齐全的前提下渲染，未覆盖接收端无缓存的情况。真机未验。
