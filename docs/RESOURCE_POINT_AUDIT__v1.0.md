- 环境：`footballfree-d2gzh9xzve789c41a`

## 结论

费用大头不是存储，也不是云函数算力，而是**客户端直连数据库的高频调用**——同一批操作在「数据库调用」和「云开发 API 调用」两个计费项里被各扣一次，合计占 96%。

数据库那 3.75 万点里，**容量只占 1.22 点，99.99% 是"调用次数"**，与存了多少数据无关。

## 三个关键异常

1. **同一批流量被计费两次。** 云开发 API 185.1 万次 ≈ 数据库调用 187.35 万次，即每次 DB 操作既算一次 DB 调用（50 次/点）又算一次 API 调用（100 次/点）。两项合计 5.6 万点 = 总消耗 96%。
2. **调用量级异常。** 187.35 万次 / 5 天 ≈ 5 次/秒，峰值 19 次/秒（69,451 次/小时），对一个体验版小程序的正常读量偏高。
3. **云函数"慢且失败率高"。** 9,032 次调用平均单次执行 10,097 ms（最高 33,711 ms），累计约 9.1 万秒；错误次数均值 50.5 次/小时、峰值 181 次/小时，累计约 6,000 次失败（失败率约 58%），而超时为 0、内存超限仅 5 次——指向业务异常或任务空跑抛错，不是资源不足。

另：**11-09 当天数据库调用已耗尽套餐额度，开始按量计费**（用量图上出现黄色「按量计费」段）。

**两个必须知道的口径问题：**

- 上表 12 个集合只解释约 **50%** 的数据库调用，还有约 9,000 次/小时（其中写入侧缺 ~3,300 次/小时）无法归到任何单集合——监控下拉列表是分页的，可能有集合未暴露，也可能存在索引/连接/监听级别的内部开销，需再用 API 侧日志或账单核对。
- 前 5 个集合取自 11-06~11-10 窗口，`job_locks` 等补充项取自「最近 7 天」预设（该页面改结束日期极易失败），占比各按自身窗口的数据库总量计算，量级可比，未精确对齐窗口。

## 处理优先级

1. **先压 `matches` + `provider_leagues` 的高频读**（两者已占约 1/4）。合并成一次云函数聚合返回、降低轮询频率或加本地缓存，可同时削减 DB 点与 API 点两份开销。
2. **查云函数 58% 失败率 + 10 秒均值执行时长**。既然超时为 0，问题在业务逻辑（空跑 throw、慢查询重试），不在配额。
3. **合并 `job_locks` 的锁 acquire/release**（读写各半、每小时 600+ 次），降低调度频率或改批量加锁。
4. 存储、CDN、AI、MySQL 均为 0，无需处理。
