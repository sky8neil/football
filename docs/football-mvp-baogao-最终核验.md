# football-mvp 三份报告最终核验

核验日期：2026-11-18。代码基线：本地 `a209232`。对照原报告 `football-mvp-baogao.md`、第一版 `football-mvp-baogao-核对.md`、第二版 `football-mvp-baogao-审查-v2.md`。本轮没有修改业务代码、数据库或线上 dist，没有执行 build、commit、push。

## 结论口径

以下区分已经证实的代码缺陷、需要特定条件触发的数据风险、可选体验调整和未实测的视觉风险。数据库只代表本机 gateway.env 所连接的 football_dev schema，不能外推成所有部署的数据现状。函数诊断与页面逻辑调用不等于微信真机视觉验收。

三份报告都有可用证据，也都有错误，不能以投票决定结论。原报告的九个大标题里揉进多个独立问题，不能按标题数量统计缺陷数。

## 一、优先处理的两项数据风险

### 1. 等级评估、重建和核对没有共用已登记的首评时间

**结论：真问题，优先级高；特定操作触发，不能说每周必崩。**

`src/domain/levels.ts:422` 在 `firstEvalAsOf === null` 时返回 1 级；`src/application/stats-rebuild-service.ts` 会把回放等级写入用户和赛季统计。当前库中有 5、6 级账户，因此不能把这一配置视作无害的未启用功能。`weekly-level-eval.ts` 只有在保护期与非保护期计算结果不一致时抛 SPEC_GAP，部分用户正常的事实不能证明整批评估可靠。

**不改会怎样：** 平时看着正常，管理员一旦执行相关统计重建，高等级账户可能被重算成 1 级；周评触发保护期分歧时会失败；一致性核对也可能把实际等级和回放的 1 级当作异常。这里说的是等级，不是积分余额全部清零，也没有证据说当前账户已经被重建降级。

**独立复核补充：** 子代理使用实际服务与内存仓储复现：周评得到 Lv.2、评估窗口20场后，对该用户重建，当前生涯/赛季等级变为 Lv.1、评估窗口变0，历史最高仍为 Lv.2、积分仍为240。重建入口按目标用户执行，不能说一次必然重置全体用户。每日一致性服务仅报告差异，不回写等级；周评遇到异常会中断后续用户及本批榜单生成，先前已提交的用户事务不会整体回滚。这些是内存场景证据，不是生产数据变更记录。

**修到什么程度：** 查实首评日期和保护期业务口径，使周评、重评、重建、一致性检查使用同一时间轴；不能随意填今天，更不能只隐藏报错。

### 2. 供应商更换比赛 ID 后，旧预测与新比赛尚未贯通

**结论：真问题，条件触发；当前六组样本没有证明丢预测或丢分。**

`provider-schedule-sync.ts` 会将旧比赛标为 `superseded_by`，新比赛沿用 `canonical_match_id`；列表、预测查找和结算仍存在按具体 `match_id` 处理的路径。`predictions.ts:158–161` 的提交接口已经按 canonical 查同组比赛的旧预测，能正确阻止重复提交；因此并非全链路都缺失 canonical 处理。没有旧预测的样本无法覆盖旧预测迁移问题。

本轮只读查询确认：6 条旧比赛均 postponed；旧比赛预测数均为 0，新比赛各有 2 条。旧、新比赛的开球日期不同：7 月的旧赛，有的新赛在 8、9 月。

**独立复核补充：** 子代理实际服务内存复现：旧赛成功提交1条预测后仍能合并，新赛详情返回 can_predict=true、my_prediction=null，再次提交被正确拒绝；为新赛准备结算时生成0条 settlement_items，旧预测没有纳入。主 agent 另行核对 `provider-schedule-sync.ts:203–248`，合并确实不检查预测数量，也不要求旧赛必须 postponed；`settlement-item-preparation.ts:35` 确实只按新赛 match_id 取预测。漏结算是可触发的代码缺陷，不能用现有6组旧赛无预测的样本排除，但仍未证明线上已经发生漏算。

**不改会怎样：** 若用户已预测的比赛以后被供应商更换 ID，新卡可能认不出旧预测，提示可预测；用户再次提交时，提交接口会正确识别同一业务比赛并拒绝，形成“页面说能预测，提交又说已预测”的矛盾。旧预测也可能无法随新赛结果结算。作废赛程还可能继续参与列表和赛程状态判断。

**纠正旧结论：** 不存在“新赛进入默认 30 天窗口，旧赛必然一起出现”的保证，两条记录各按自己的开球时间过滤；首页还显式按选中日期请求。旧记录是否显示要按具体日期核验。详情查不到预测也不等于返回 500。

**修到什么程度：** 将比赛列表、详情、提交、个人记录、结算按同一业务比赛身份处理。仅过滤旧卡可以消除部分显示问题，但不能解决旧预测归属与结算。

## 二、建议纳入功能修复的明确问题

### 3. 登录入口与 HTTP 登录态恢复

**结论：入口错误确定成立；失效会话问题限 HTTP 模式及对应触发条件。**

`profile.wxml:7` 的“登录”绑定 `onSessionTap()`，但 `profile.js:288` 导航至设置页，和设置按钮共用处理函数。`miniprogram/config.js:4` 当前配置为 HTTP，因此失效 token 恢复也是当前模式内的问题，而非只在未使用的分支里。

**不改会怎样：** 从“我的”页点登录会进入需要登录才能使用的设置页，无法就地完成登录；服务端会话已失效、本地仍认为有效时，即便进入正确登录页也可能反复收到 401。单纯重启不保证恢复，可能要等本地会话过期或清理失效缓存。

**修到什么程度：** 登录与设置分别导航；明确收到会话失效时如何恢复登录并返回原页面。不能只改按钮文字。

### 4. 首页无法稳定展示已预测比分和得分，完场说明还依赖本地是否提交

**结论：真问题；第一、二版关于“刷新清空提交缓存”的解释不成立。**

`MatchListItem` 不返回 `my_prediction`；`matches.js:283` 只从 `submittedMap` 取预测。该字典在文件中只有初始化、读取和提交成功写入，没有在 `loadFirstPage()` 清空。

**不改会怎样：** 本页刚提交的比分可以暂时显示；重新进入页面、在详情页提交或换设备后，首页认不出具体预测比分，可能显示“未预测”。有全场比分的比赛也可能仍标“待结算”。用户容易误以为提交失败或积分没有到账，要进详情、记录页才能核实。

`buildCardState()` 实际运行：完场、有全场比分、无本地 submitted → `待结算 / 未预测`；提供本地 submitted → `FT / 已提交…`。可见“是否有全场比分”和“我是否参与”被错误耦合。非参与者也不应因没预测而看到“待结算”。

**边界：** 常规已有预测时服务端 reason 仍为 ALREADY_SUBMITTED，会隐藏预测按钮；不能笼统说一定能再次提交。本轮没有证据说明积分真实丢失。

**修到什么程度：** 首页回显来自服务端；全场比分、是否结算、我的预测分别表达。

### 5. 排行榜“我的积分”受是否加载到自己的列表行影响

**结论：真问题，是展示取数错误，不是积分计算错误。**

`rankings.js:455` 从当前 `merged` 找自己；接口 `me` 只带排名身份，不带本人的指标。服务端每页 10 条，只公开前 20 名。

本轮直接调用页面逻辑：第 15 名首屏“第 15 名 / —”，追加包含自己的第二页后变成真实数值；前 20 以外显示百分比但积分仍为“—”。

**不改会怎样：** 用户明明有排名，却看不到自己的积分或评分；第 11—20 名需点加载更多才出现，20 名外无法通过加载更多补齐。小规模测试账户不一定能暴露。

**修到什么程度：** 服务端独立返回当前用户的该榜指标，不依赖公开列表分页。

### 6. 群榜身份变化后，重试仍停在失效范围

**结论：真问题，但不是所有排行榜都不可用。**

`rankings.js:195` 发现所选群不在最新成员列表，仅设 error 后 return，没有清除所选群或提供此状态下的直接恢复动作。

**不改会怎样：** 退群或群被解散后，原群榜报错，点重试仍请求旧群。用户可能需要主动切回全站或重新进入，重试本身不能解决问题。

**修到什么程度：** 成员变化时更新群列表，并提供切回可用范围的明确路径。

### 7. 预测记录队徽全占位，其他页面还缺部分别名

**结论：真问题，两层问题都要处理。**

`team-presentation.js:11` 把调用方传入的 team 交给按名字匹配的 `getTeamLogo()`；记录页只传 team_id。注册表真实调用统计：总数 112；只传 ID 时占位 112；传 source_name 后仍占位 45。

**不改会怎样：** 用户在预测记录里看到的都是通用队徽，比赛辨识更慢；首页、详情等带名字的页面也有部分球队没有正确队徽。不会改变预测、比分和积分。

**修到什么程度：** 使用稳定球队身份解析已有本地队徽，并补齐确认过的别名；仅补传 name 不能解决全部问题。不必因此重做球队中文名方案。

**同项修复：主队显示及设置候选不能依赖近期赛程。** `profile.js` 无缓存时通过赛程找主队；`settings.js:34` 仅名称解析使用注册表，`:41–54` 的候选球队仍由赛程收集。球队不在查询窗口时，成长页可能显示占位队徽，设置页也可能找不到该队、无法选为主队。这是条件性功能缺陷，纳入本项修复，不能把“设置页已用注册表”扩大成整个选队流程不受影响。

### 8. “本赛季成绩单”有数据却始终显示横杠

**结论：功能缺项，建议补齐，不是算错数据。**

`profile.wxml:26` 本赛季积分和精确命中写死为“—”；`SeasonLevelData` 只提供等级和场次，未提供对应统计字段。

**不改会怎样：** 用户切到本赛季，只能看到场次，积分与精确命中一直像没加载好；即使有成绩也不能在这里查看。生涯统计不因此受影响。

**修到什么程度：** 从相同等级赛季统计源取 points/exact_hits 并展示，不能直接拿生涯积分冒充，也不能混用联赛赛季和等级赛季。

### 9. 满足场次、仍是 Lv.1 的用户可能出现误导升级进度

**结论：原报告这一细项确实有依据，前两份复核反驳不完整。**

整个 `buildLevelView()` 已被使用，不等于其中的特定分支正确。`profile.js:128` 在 Lv.1 时传 nextThreshold=null；buildLevelView 在 isRated=true 且 bPoints 为数值时可能把 null 当 0 比较。

本轮直接调用：level=1、isRated=true、remainingToRated=0、nextThreshold=null，bPoints=0 或 50 都得到 reached、100%、“评估积分已达门槛”；bPoints=null 才得到 pending。这是条件触发，不是所有 Lv.1 都会错。

**可达场景：** 用户不足20场时已经周评，留下数值型旧评估积分、等级仍为1；周中达到20场后，接口 is_rated=true，但尚未再次周评，便可能走入错误满格分支。第一次满20场且从未评估的用户 b_points=null，会正确显示等待评估，不能把这类用户也算成满格故障。另一个“够场次且 isRated=false”的待评文案分支在当前接口约束下不可达；死的是这个分支，不是整个展示模块。

**不改会怎样：** 部分已够场次、仍待周评的新人会看见满格升级进度，误以为马上升级，实际等级不变。不会凭这段前端代码真的改掉服务端等级。

**修到什么程度：** 明确待首评、未定级、已定级升级的区别；等级继续服从后端，不在前端自行判级。

### 10. 截止后、开球前，“大家预测”对已提交者仍锁定

**结论：真问题，但时间范围有限。**

`predictRejectReason()` 优先返回 ALREADY_SUBMITTED；`crowdPlan()` 在 scheduled 且此 reason 时不请求分布，未提交者截止后则可能按 CLOSED 请求。

**不改会怎样：** 同样已经截止，没参与的人能看大家怎么选，提交过预测的人却还被锁住。比赛进入 live 或 finished 后会正常请求，不能说完场仍被锁死。

**修到什么程度：** 用服务端截止状态决定分布开放，不修改已有预测拒绝理由的领域优先级，也不提前泄露未截止的分布。

### 11. 加群失败后的恢复动作缺失，创建群成功页数量写死

**结论：两个较小但明确的功能问题。**

`groups/join.wxml:19` error 只有错误文本，没有重试或回输入动作；`profile.js:279` 创建群后固定传 owned_count=1。

**不改会怎样：** 加群成功或已是成员后，二次查询群列表失败、或未找到目标群，会进入没有恢复按钮的错误态，用户需要退出再进。普通邀请码错误、限流等仍可在输入态重试，不能概括为所有加群失败都会卡住。从“我的”创建第二、第三个群，成功页仍可能显示“1 / 5”。后端创建上限不因此失效，只是成功页说错数量。

**修到什么程度：** 错误态提供可执行的恢复动作；数量取真实自己创建的群数，不能拿参加的群总数代替。

## 四、需微信环境复现后再定

首页 `.feed` 两段样式对 bottom padding 存在覆盖，但同时有高度计算；不能只减两个数字就断言遮挡多少像素。当前无真机或微信开发者工具复现证据。

**如果真的遮挡而不改：** 最后一张比赛卡或加载更多按钮可能被底栏盖住。**当前决定：** 留作真机验收项，不写成已证实故障，不扩大成全站样式重构。

## 五、不采纳的结论与方案

- 不采纳“完场后已提交用户仍看不到大家预测”。实际执行 crowdPlan：scheduled + ALREADY_SUBMITTED → locked；live/finished + ALREADY_SUBMITTED → fetch。真问题只在截止后、仍 scheduled 的窗口，不另报一条完场故障。
- 上述截止后窗口仍应修：已提交的人被锁，未提交的人可能可看。后果是开球前这一段时间信息不对称；建议以服务端截止状态决定是否开放，不改变预测拒绝原因的领域优先级。
- 不采纳“loadFirstPage 清空 submittedMap”，当前代码没有这一步。
- 不采纳“整个 level-presentation.js 没被调用”，但保留它的 Lv.1/null 阈值缺陷。
- 不采纳“114 队、44 队缺别名”，本轮真实注册表诊断为 112、45。
- 不采纳“所有周评必崩”“积分清零”“已经有用户丢分”等无证据扩大表述。
- 不采纳“只加一行 superseded_by 过滤就完整修复赛程合并”。读列表、历史记录、结算需要分别处理业务身份，不能盲目让所有仓储读取都忽略旧比赛。
- 不重启此前撤销的 DATA-02，不把忽略的 UX-05 写成已修复。

## 六、建议开发顺序与验收重点

1. 等级时间轴和赛程身份：先确定真实业务基线，用已有预测被换 ID、已有高等级被重建等场景验证；不先对现有库执行重建试错。
2. 登录、首页回显、排行榜个人指标与群范围恢复：直接影响用户完成操作和核对成绩。
3. 队徽、赛季成绩、Lv.1待评估、加群恢复与创建数量：补齐明确缺项。
4. 开球前截止窗口的大家预测开放；其他展示微调按产品范围合并做。
5. 底栏遮挡交给微信环境验收，证实后再做最小修复。
