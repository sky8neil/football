### CR44-01（P2，延续 CR43-04）：预算耗尽仍可阻挡后续有主源数据的滞留比赛

**位置与调用链**

- `src/application/provider-stale-recovery.ts:187`：每个日期组先读取开球当日及次日的主源数据。
- `src/application/provider-stale-recovery.ts:218`：主源处理后仍滞留的候选进入副源查询；仅已离开活跃集合的比赛提前标记为已处理。
- `src/application/provider-stale-recovery.ts:260`：完成整个副源阶段后才把该日期组全部加入 `processedIds`。
- `src/application/provider-stale-recovery.ts:286`：主源、副源的预算拒绝共用同一分支，直接结束整轮；`:294` 只按完整处理的连续前缀推进游标。
- `src/provider/registry.ts:408`、`:521`：真实客户端的显式副源请求会把预算拒绝传播给恢复服务，故不是仅测试桩可触发的异常类型。

**场景 A：副源无额度，但后续主源仍可恢复比赛。** 最早的滞留日期在主源无记录，配置的副源 OpenFoot 额度耗尽；后续日期的一场比赛仍有主源 FT。当前代码在第一个日期组的副源预算错误处整轮返回，后续主源日期根本不被查询。第一个日期组未完整处理，持久游标仍为空。只要副源额度持续被其他任务耗尽，就会重复此过程。

**主审实际执行结果：**使用当前快照编译产物中的真实 `ProviderStaleRecoveryService` 和 `InMemoryRepository`，沿用既有测试的 11 场建赛及映射方式，将比赛分布到 9/1～9/11；主源始终可请求，9/11 可返回第 11 场的合法 FT；副源返回 `ProviderBudgetDeniedError('day_limit')`。连续三个不同日期的恢复轮次均为：

```text
kind=completed, items_read=0
primaryDates=[2026-09-01, 2026-09-02]
secondaryDates=[2026-09-01]
cursor=null
第11场 match_status=scheduled
```

**场景 B：每轮剩余主源额度只有一次，首个日期组没有 FT。** 一个日期组需要开球当日和次日两次日期查询；第一次返回空，第二次预算拒绝。当前仅缓存本轮成功查询的数据，既未持久化日期组内部的查询位置，也没有可推进的已处理候选。主审连续三轮重置可用额度，各轮均重复查询 9/1、在 9/2 被拒绝，`items_read=0`、`cursor=null`。这不是“完全没有额度”的情形，而是已有成功查询无法被下轮续用。

**影响：**主源有额度且后续有合法数据时，仍可能被最早的不可恢复日期和副源预算挡住；低额度时每轮消耗相同日期请求却没有可累积进度，CR43-04 所要求的轮转仍未闭环。

**最小修复方向：**区分主源和副源的额度终止条件，避免副源预算拒绝阻断后续可执行的主源查询；为尚未完成的日期组保留可跨轮继续的进度，或采用能保证已尝试候选最终轮转的策略。保留当前已取得 FT 必须落地的行为。

**最小回归：**① 最早日期主源无数据、副源额度为零、较晚日期主源有 FT，连续轮次应能访问并恢复较晚比赛；② 每轮仅能成功一次日期请求且首个日期无 FT，后续轮次应继续推进，不能无限重复同一日期组。

**现有测试边界：**新增 CR43-04 用例使用主副源共用的每轮 6 次计数，能完整处理至少一个日期组并产生连续前缀；没有覆盖“只有副源预算不足”和“额度不足以完成首个日期组”。主审复现为内存服务链，不是上游真实配额实验或 PG 集成验收。

### CR44-02（P2，本轮新发现，关联 CR43-06）：动态主队资料持久缓存不失效，运营补齐后旧名称和队徽不会更新

- `miniprogram/services/teams.js:147`～`:155`：从微信持久存储读取 `team_name:`、`team_logo:`；只要两者存在且队徽不是占位图，就返回 `needsRemoteLookup=false`。

**触发：**自动入库的新球队已有英文名和真实远程队徽，但中文名尚未补齐。用户或分享接收者先打开页面，缓存英文名及队徽。运营随后补齐中文名或替换队徽，用户再次打开分享卡或公开主页。

**实际行为：**持久缓存的英文名也被视为有效名称，真实但过期的队徽也被视为完整资料，页面直接跳过远端查询。即使结束进程、内存目录缓存已清空，也不会再查询该球队，因此不受 `ACTIVE_TEAMS_CACHE_TTL_MS=5分钟` 限制。

**主审实际执行：**运行当前 `teams.js` 的真实解析函数和 `team-presentation.js`，使用微信存储内存替身模拟跨启动保留的数据。首次服务端返回 `name=Promoted FC, name_zh=null, logo_url=logo-v1.png`，解析后正常缓存。随后把服务端改为中文名“升班马竞技”和 `logo-v2.png`，调用 `clearTeamsCache()` 清空内存目录后再次执行页面所用的同步判定，结果仍为：

```text

favoriteTeamLogo=https://example.com/logo-v1.png
needsRemoteLookup=false
服务端请求次数仍为1
```

**影响：**后台补齐升班马资料后，曾访问过该队的用户仍长期看到旧英文名和旧队徽，而没有缓存的新用户可看到新资料。需要清除微信本地缓存或其他页面偶然覆盖缓存才能收敛，动态资料下发仍不完整。

**最小修复方向：**持久缓存可继续用于首屏展示，但不应永久阻止远端刷新；可让包外球队按现有短期目录缓存周期重新确认资料，或给持久缓存增加明确的失效依据。

**最小回归：**先缓存包外球队英文名及真实队徽 → 服务端补中文名并换队徽 → 保留微信存储、清空进程内缓存 → 再次打开分享卡和公开主页，最终应以服务端最新资料展示。

**验证边界：**主审已执行实际共享解析函数并核对两个页面的提前返回条件；未跑微信开发者工具或真机。原来的“接收端没有任何缓存”场景已经接上远端补全，本项没有把该原问题重复计为未修。

### CR44-03（P2，本轮新增核对场景，关联 CR43-06）：已选包外主队停用后，新设备无法显示其名称和队徽

**位置与调用链**

- `src/application/profile.ts:136`、`src/application/share-card.ts:435`：正常用户的公开资料和分享卡仍返回已选的 `favorite_team_id`，不会因该队停用而清空主队。
- `miniprogram/services/teams.js:76`、`:163`：为包外主队补全资料时，唯一入口是可选球队目录 `/v1/teams`。
- `src/api/v1/teams.ts:69`：该目录仅保留 active 球队，停用队即使仍存在数据库也不返回。
- `miniprogram/pages/share-card/share-card.js:494`、`miniprogram/pages/public-profile/public-profile.js:194`：解析结果为空时直接保留原兜底，无法补全已选主队的显示资料。

**触发：**用户在球队 active 时合法选择一支包内不存在的球队，球队后来停用；其他没有该队本机缓存的设备再打开该用户的分享卡或公开主页。

**实际行为：**主队关系仍然存在，但显示资料查询错误地依赖“当前允许新选择”的 active 集合。接收端有主队 ID，却只能显示“已选择球队”与占位图。这与“停用球队不应继续出现在设置候选中”是两个不同要求：设置入口应限制新选择，展示既有主队仍需要解析已有 ID。

**执行证据：**主审使用实际 `ProfileMutationService.updateMyProfile()` 在 active 状态保存主队，以实际 `/v1/teams` 处理器接入真实小程序共享解析函数；active 对照正常得到“升班马竞技”及远程队徽。随后把仓储球队状态改为 inactive，使用无微信缓存的新解析实例读取实际公开资料，结果为：

```text
publicProfile.favorite_team_id=原已选球队ID
GET /v1/teams items=[]
同步展示=已选择球队 / team-placeholder.png
resolveFavoriteTeamRemote(...)=null
```

独立复核还执行了真实公开主页及 teams 服务的 VM 链路，页面维持 ready 状态但主队名称/队徽降为占位；分享卡为同构逻辑核对，未单独执行停用场景的完整页面流程。

**影响：**同一用户的主队在有缓存的老设备可以显示，在新设备或清空缓存后丢失名称、队徽；换季停用队或运营调整状态后，已有主队展示无法闭环。

**最小修复方向：**将“可新选择的 active 球队集合”与“已选球队 ID 的展示解析”区分。保留设置页 active 过滤；已选球队的公开展示可以由资料/分享接口带出其显示字段，或通过按 ID 读取既有球队资料完成补全，不必把 inactive 球队重新加入选择器。

**最小回归：**active 包外球队设为主队 → 停用该队 → 无缓存设备打开公开主页和分享卡，仍正确显示该主队资料，同时设置候选中不得出现该停用队。

**验证边界：**主审确认实际保存、公开资料查询、球队目录处理器及共享展示解析；公开主页完整 VM 场景由独立复核执行。未做微信真机验证，未访问生产服务或数据库。
