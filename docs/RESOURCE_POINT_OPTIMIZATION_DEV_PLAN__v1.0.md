# 云开发资源点优化开发方案

- 版本：v1.0
- 日期：2026-11-10（Asia/Shanghai）
- 项目：football
- 目标环境：`footballfree-d2gzh9xzve789c41a`
- 服务：`api` 普通云函数 / 文档型数据库 / `football_test` 资源命名空间
- 输入依据：[资源点审计 v1.0](./RESOURCE_POINT_AUDIT__v1.0.md)、现有代码和本次云端诊断记录。
- 状态：开发计划，尚未实施。本文件中的目标值、拟新增配置和数据结构不代表当前代码已经支持。

## 1. 方案要解决什么

大白话：后台现在像一个每分钟巡视全部文件柜的工作人员。即使没有新比赛、历史比赛已经结清，也会继续翻记录、检查状态和申请锁。优化后应当先看待办清单，只处理到期、发生变化或尚未完成的事情。

优先减少数据库实际读写次数，连带减少相关 SDK/API 调用和函数运行时间。保留比赛期间的必要更新，以及结算的事务、幂等、版本校验和失败恢复能力。

本轮不以迁移数据库、引入 Redis、增加机器或缩短函数超时为主要方案。页面和榜单缓存根据后续观测再安排，不作为第一批工作的重点。

## 2. 审计结论及口径修正

### 2.1 可用于确定方向的数据

审计区间为 2026-11-06 至 2026-11-10，记录总消耗约 58,242 点。其中数据库约 37,500 点、环境 API 调用约 18,500 点，两项合计约占 96%。存储容量消耗很小。

数据库调用约 187.35 万次，小时峰值 69,451 次；读写约为 64:36。`matches`、`provider_leagues`、`settlements`、`job_locks` 是已经识别出的主要集合。`settlement_items` 的实际业务处理量却很低，提示需要排查大量检查是否没有转化为有效工作。

### 2.2 实施前必须修正的解释

1. **不能据此认定客户端直连数据库。** 小程序现有代码通过 `wx.cloud.callFunction` 请求后端；云开发 API 计费项包含 SDK/API 调用。数据库调用和 API 次数接近，只能作为关联线索，不能证明全部请求来自客户端或每次操作必然一一对应两个账单项。
2. **不把“合并成一个云函数”当作主要节省来源。** 当前已经通过云函数访问数据库；只有减少函数内部实际发出的请求，才能明确减少这部分操作量。
3. **失败率必须按同一窗口重算。** 审计的“约 6,000 次失败 / 9,032 次调用”约为 66%，与文档中的 58% 不一致。最终以相同时间范围的计数及平台指标定义为准。函数平台失败、业务返回非 200、正常跳过要分开统计。
4. **集合统计不能直接相加得出精确占比。** 部分数据使用最近七天窗口，目前只解释约一半调用。剩余调用尤其是写入，不能未经验证就归因于索引、监听或平台内部开销。
5. **120 秒是上限，不是每次固定执行时间。** 保留当前上限，优先缩短实际工作和等待时间。

### 2.3 已观察到的云端状态

2026-11-10 重新运行 `{"action":"diag"}` 后，函数完成返回，未再触发原来的三秒超时。28 个所需集合、读写探针和事务探针通过；环境变量及命名空间检查通过，但运行时环境 ID 为 null，环境匹配检查失败，诊断应用状态为 503。控制台测试未取得微信用户身份。

因此不能把平台显示“测试成功”等同于应用诊断全部通过。后续仍需验证真实小程序上下文，并单独排查运行时环境 ID 的取得方式。

## 3. 可定位到代码的优化点

| 位置 | 当前行为 | 开发方向 |
| --- | --- | --- |
| `src/application/settlement-timer.ts` | 每轮遍历赛季比赛；已完场且未作废的比赛会进入后续检查，即使已完成结算 | 数据库直接查询待结算、待更正和到期重试任务 |
| `src/cloud-function/runtime.ts` | 每分钟 Timer 判断多类任务是否到期，随后执行结算检查 | 建立到期调度入口，减少空跑和重复状态读取 |
| `src/provider/registry.ts` | `dueLeagues()` 调用 `orderLeagues()` 后再次读取联赛状态 | 同一轮复用查询结果，再评估批量读取 |
| `src/application/provider-sync-job.ts` | 部分可重试错误在函数内 sleep，期间存在锁续租 | 保存下次重试时间，结束本轮；后续领取恢复 |
| `src/provider/budget.ts` 及 CloudBase usage store | 请求预算维护多个计数桶 | 先测量实际操作数量，再优化重复读取；保留跨实例预算一致性 |
| `scripts/cloudbase-deploy-function.mjs`、`cloudfunctions/api/config.json` | 两处声明每分钟 Timer | 同步维护部署声明和线上设置，防止重新部署覆盖降频配置 |

说明：同步服务已有变化判断和业务状态机。应通过调用计数确认哪些分支仍产生重复操作，不能先假定全部同步都是无条件重复写入。

## 4. 实施任务与顺序

### P0：临时止损及补齐观测

**RP01：测试环境临时降频。** 将 Timer 由每分钟一次改为每十分钟一次，适用于当前调试阶段。同步调整两处部署声明并回读线上触发器；确保只有一个有效调度触发器，不出现新旧触发器并存。记录变更时间，便于对比。

代价：比分、完场核对和结算可能延迟；任务积压也可能按联赛分批消化。实时性测试时按约定窗口恢复频率。降频不会恢复已经扣掉的资源点。

**RP02：统一统计窗口。** 按相同起止时间、时区和小时粒度导出数据库总读写、全部集合读写、函数调用及失败计数、执行耗时、资源点分类。标注未完成统计的时间桶，不把图末尾的零直接当作消耗归零。

**RP03：增加低成本任务摘要。** 每轮记录任务类型、联赛、触发来源、到期/跳过原因、读写操作数、候选比赛数、实际变化数、结算处理数、耗时、错误码及重试次数。优先在数据库适配器和任务入口计数，每轮输出一条摘要；不为每次查询另写数据库日志。记录调用口径和事务重试，避免将本地计数直接当作平台账单。

日志不得包含密钥、OPENID、完整请求体或赛事源完整响应。初期对成功空跑采样，对失败保留错误码与有限样例，并设置短期保留策略，避免观测本身成为新的开销。

**RP04：失败分类。** 区分真正异常、数据格式错误、配额/鉴权错误、锁竞争、到期未满足和无比赛窗口。正常跳过返回结构化结果；保留真实失败，不通过吞错降低失败率。

验收：统计窗口对齐；可以按任务解释主要调用；失败样例可归类；部署后触发器频率和数量与预期一致。

### P1：先去掉明确的重复工作

**RP05：结算改为查询待办。**

- 首次结算：只选符合现有结算条件且没有完成当前结果版本的比赛。
- 更正结算：只选结果版本高于已结算版本、且满足现有更正规则的比赛。
- 失败/进行中结算：只恢复已到重试时间或租约允许恢复的任务。
- 已完成且结果版本无变化的比赛退出高频扫描。
- 所有筛选优先在数据库完成，分页并限制每轮数量。数据库不支持直接比较两个字段时，可维护可查询的待办标记或独立待办记录；不将全量读取后过滤当作最终实现。
- 待办的产生必须与比赛结果状态更新保持一致；复用现有事务边界。领取任务后再次核对结果版本，防止读到过期候选。
- 低频兜底检查负责发现漏标、过期租约和未完成更正；采用分批游标，避免每天产生一次无限全表扫描尖峰。

大白话：只找没结完和需要改账的比赛。风险是漏标导致漏结算，因此保留版本核对与兜底。禁止移除事务、幂等和已入账 item 的恢复规则。

**RP06：联赛状态同轮复用。** `orderLeagues()` 与 `dueLeagues()` 共用本次调用读取的状态；同轮相关任务可按明确键复用。成功写入后更新或失效缓存。缓存只作为减少读取的手段，领取任务和预算检查仍以数据库为准。

验收：已结清的历史比赛数量增加，不再导致每轮结算读写近似线性增长；同轮相同联赛状态不重复读取；首次结算、更正、失败恢复和并发实例测试通过。

### P2：控制重试和锁开销

**RP07：持久化延期重试。** 将分钟级 sleep 改为记录 `attempt_count`、`next_attempt_at`、最近错误码并结束本轮；下一次调度到期后恢复。字段名称为设计建议，开发时与现有 schema 对齐。

- 网络临时故障、部分服务端错误：指数退避并加入抖动。
- 配额耗尽：等待额度恢复；尊重上游恢复时间。
- 鉴权或固定格式错误：停止无效自动重试，暴露待处理状态。
- 明确最大尝试次数和人工重试入口，避免无限重试。
- 区分“本轮成功处理任务”与“任务延期”，不要将延期标为业务同步成功。

**RP08：锁只覆盖实际工作。** 任务到期判断、比赛窗口判断在锁前完成；锁内再次确认任务资格。按任务/联赛粒度保留互斥，减少重复 acquire/release；根据租约和实际耗时调整续租，确保中断可恢复、锁失效后旧 worker 不再写入。不取消锁，不把所有同步合成一个大锁。

代价：故障恢复可能稍慢；状态与租约管理复杂度增加。收益来自减少无效锁操作和等待，不能以牺牲并发正确性换取。

验收：等待下一次重试期间不占用函数；无任务时不反复申请业务锁；并发领取、函数中断、租约过期、旧 worker 继续执行等场景不会重复入账或重复处理。

### P3：按比赛窗口调度，并用数据库筛选候选

**RP09：增量候选查询。** 实时任务按联赛、比赛状态和时间范围查询，只读必要字段；同一轮多个任务可共享候选结果。避免每次加载完整赛季后在内存筛选。索引根据实际查询条件补充，先核对既有索引可否复用。

**RP10：到期任务调度。** 先在 P1/P2 结果上评估集中任务表：保存任务范围、下次执行时间和领取租约，查询到期记录并原子领取。任务表不是全局大锁。定时器分辨率决定最短更新频率，不能在每十分钟唤醒的前提下承诺三分钟更新。

初始建议节奏：

| 场景 | 目标间隔 | 说明 |
| --- | --- | --- |
| 当前开发测试 | Timer 每十分钟 | 临时止损，接受更新延迟 |
| 无相关比赛、无待办 | 三十至六十分钟 | 最终实现应同时减少无效唤醒和数据库访问 |
| 临近开赛 | 十至十五分钟 | 核对延期、开球时间及状态 |
| 正在比赛 | 二至三分钟 | 若需要一分钟更新，重新评估成本 |
| 刚完场、等待核对 | 三至五分钟 | 达到确认条件后及时结算 |
| 已结算且无更正 | 退出高频检查 | 保留低频更正核对 |
| 未来赛程 / 全赛季核对 | 暂保留十二小时 / 每日 | 先验证当前间隔及联赛轮转没有重复执行 |

实现选项：第一版可以保留一分钟轻量调度，但要求绝大多数轮次只读取极少状态；后续通过控制面更新唤醒频率或安排活动时段高频触发进一步降耗。必须避免多套定时器重复消费。具体方案在调用计数结果出来后确定。

代价：延期、加时、点球、比赛中断和迟到更正可能超出原窗口。窗口同时依据业务状态与时间缓冲，不能只按预定结束时间停止更新。无效/缺失的窗口数据需有低频兜底。

### P4：按观测结果减少重复写入

**RP11：批量读取和同轮映射缓存。** 同批赛事复用球队、赛事映射；在 SDK 查询限制内分批加载已有记录，降低逐场重复查询。先分页再处理，避免大批量一次装入内存。

**RP12：变化才写。** 核对已有变化判断，补齐真正不变数据的快速返回；定义关键业务字段集合。比分、比赛状态、开球时间和结果版本变化必须进入原有业务状态机，不能通过简单去重跳过。

**RP13：预算和快照专项。** 对 `provider_usage`、`provider_keys`、`provider_snaps` 等尚未解释清楚的读写补充观测。预算预留、释放和多实例额度控制保留一致性；不能为了少写计数而突破上游额度。快照按实际用途去重、设保留规则，清理历史数据另行执行，不作为本轮自动删除步骤。

代价：比较字段错误会漏掉更新，批量查询过大会增加内存和延迟；审计数据减少可能影响追溯。必须定义内容、批量上限和保留策略后实施。

## 5. 边界及必要保护

- 真实用户的预测提交、身份鉴别、积分及结算校验保持实时，不使用过期公共缓存完成资金/积分判断。
- 六联赛业务范围先保留；缩小测试联赛范围是可选止损手段，不作为正式功能缩水。
- 缓存不能代替分布式锁、数据库事务和原子额度预留。
- 并发数据库查询可以缩短耗时，但不必然减少请求次数；必须分别统计时长和次数。
- 索引帮助查询效率，不能消除代码主动发送的重复查询。不会仅为了省点数批量删除已有索引。
- 运行时环境 ID 为空的问题单独修复：从可信运行时上下文核实来源；不得拿配置值回填为“实际环境”以使诊断假通过。

## 6. 节省目标与计算方法

下表仅为审计区间的情景估算，假定数据库与 API 合计 56,000 点、其他 2,242 点不变：

| 数据库与 API 消耗下降 | 同一区间总点数估算 |
| --- | ---: |
| 50% | 30,242 |
| 80% | 13,442 |
| 90% | 7,842 |
| 95% | 5,042 |

不是月度预测或收益承诺。数据窗口不一致、约一半请求未归属，且用户量和比赛密度会改变结果。第一批目标为在可比负载下减少后台数据库请求至少 50%；后续以 80%～90% 为努力目标。若未达到，按摘要继续定位而非单纯加大降频。

分别报告：每次有效同步的读写次数、每场有效结算的读写次数、空跑每轮调用数、小时总调用及每日资源点。成功减少调用与任务没有正常工作必须能区分。

## 7. 测试和验收

### 7.1 实施时需要覆盖的测试

1. 已结算比赛不进入高频待办；新完场、结果更正和到期失败任务能进入。
2. 部分 item 已入账后的重试不重复加分；新结果版本不会被旧 worker 覆盖。
3. 两个实例同时领取同一任务，只允许一个有效执行；锁失效、中断后可以恢复。
4. 延期重试未到时间不调用上游；到期恢复；配额耗尽和鉴权错误不会形成重试风暴。
5. 同轮状态复用有实际调用计数断言；更新后缓存失效正确。
6. 无比赛、延期、加时、点球、异常中断及跨日场景的窗口判断。
7. 相同赛事响应重复同步不产生无意义业务写入；关键字段更正仍被处理。
8. 候选记录多页、单批失败、任务积压和兜底补偿场景。

按实际改动运行对应测试，随后运行 `npm run typecheck`、`npm run build` 与 `npm run cloudfunction:build`。云端完成环境诊断和真实小程序请求验证；平台“测试成功”不足以代替应用返回码、检查字段和业务结果的核对。

### 7.2 云端对比

- 先记录基线，再用相近联赛数量、比赛数量、用户量和观测时段对比。
- 至少覆盖一个完整比赛日及一个无比赛时段，标注同步初始化、补数据和人工测试。
- 检查读取、写入、函数调用、实际执行时长、失败分类、同步新鲜度和结算延迟。
- 平台统计完成后再对比资源点；统计延迟期间不凭余额立即宣布收益。
- 验收无漏同步、无重复入账、可恢复的失败重试；实时窗口和结算延迟符合约定。
- 无比赛且无待办时，空跑保持小而稳定；历史已结算比赛增加不应显著推高每轮调用。

## 8. 发布、兼容与回退

1. 每阶段独立提交与验收，避免一次同时修改调度、结算、预算和数据存储结构。
2. 如新增字段或待办集合，先补 schema、索引和兼容读取；分批回填存量未完成任务，设置游标与速率上限，避免部署后触发全量风暴。
3. 部署前校验调度声明、线上触发器、超时和环境变量，确认没有重复定时器。部署后回读配置。
4. 先在测试环境观察少量任务及一个联赛，再覆盖六联赛完整比赛日。
5. 明确每阶段配置开关和旧版本兼容方式。回退保留新增数据和审计记录，不能用删除业务数据实现回退。
6. 正确性出现问题时暂停受影响的同步/结算任务，保留待办供修复后重放；调度频率恢复需显式执行，不能因代码回退意外恢复高频风暴。
