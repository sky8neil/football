### CR42-01（P1，切片 9）：读取无正式比分的比赛时，管理表单沿用上一场比分并能提交为正式赛果

- **位置**：`admin/app.js:428–435`，提交路径 `admin/app.js:454–458`；后端接收路径 `src/application/admin-result-correction.ts:173–217`、`234–239`。
- **触发场景**：先读取已有正式比分的比赛 A，例如 `4:1`；随后把 `match_id` 切换为一场已完场、等待人工补录的比赛 B（`result_version=0`，正式比分为 `null:null`），点击“读取比赛”。
- **实际行为与根因**：B 的版本被更新为 `0`，但比分输入框仅在返回值非 `null` 时才赋值，因此仍显示 A 的 `4:1`。提交处理器直接组合当前 B 的 ID、B 的版本和输入框中的旧比分。后端无法知道这两个比分来自另一场比赛，会正常追加 B 的正式赛果。
- **影响**：连续处理多场比赛时，操作员可能将另一场的比分补录到 B；后续结算将以该错误正式赛果为依据。这是正常管理操作产生的数据串场。
- **验证证据**：执行现有 `admin/app.js` 的真实事件处理器和 `admin/api.js`，观察到发往 B 的请求体为 `expected_result_version=0, regular_home_score=4, regular_away_score=1`；将同一请求体传给未修改的 `AdminResultCorrectionService` 与现有 `InMemoryRepository`，读回 B 的比分为 `4:1`、`result_version=1`。未连接线上数据库。
- **最小修复方向**：读取目标比赛时同时覆盖两个比分字段；服务端为空时将对应输入框清空，并使读取结果与目标比赛保持一致。
- **最小回归场景**：A 有比分 → B 无比分；B 读取后比分框必须为空，用户补录前不能提交沿用的 A 比分。
- **现有测试缺口**：`admin/admin-frontend.test.mjs` 覆盖客户端、分页器、DOM ID 和模板文本，没有执行连续切换比赛的页面事件流程。

### CR42-02（P2，切片 9）：管理端筛选请求乱序返回时混入旧列表并覆写分页状态

- **位置**：`admin/app.js:128–139`、`152–206`；同类模式还存在于球队列表 `213–222`、`233–275` 和审计列表 `282–295`、`307–320`。
- **触发场景**：异常列表的 `open` 请求尚未返回，切换为 `resolved` 发出新请求；新请求先返回，旧请求后返回。无需断网或异常响应。
- **实际行为与根因**：列表清空发生在发出请求前；响应回来后没有检查它是否仍属于当前筛选，直接提交分页器并追加行。先返回的新列表显示后，旧响应继续追加旧行，分页按钮也采用旧响应的状态。
- **影响**：筛选器显示 `resolved`，表格中却混有 `open` 记录；翻页可能继续使用另一筛选条件的游标。
- **验证证据**：用可控 Promise 使两次正常 API 响应逆序完成，实际运行现有异常列表函数；当前筛选为 `resolved`，最终表格同时出现 `NEW_FILTER` 和 `OLD_FILTER` 两类行。球队/审计列表为同构代码核对，未另外做浏览器操作验证。
- **最小修复方向**：各列表使用递增请求序号，仅当前请求可以更新表格和分页器；在确认响应有效后替换列表内容。
- **最小回归场景**：两次筛选请求逆序完成，最终仅保留最新筛选的行和分页状态。复用现有测试方式即可，不需要额外测试框架。
- **与 v4.1 的关系**：`CR-30` 已修复筛选重置游标及翻页失败回滚；本项是多个成功响应之间的时序问题，并非重复报告原问题。

### CR42-03（P2，切片 5）：映射工具只读确认与应用逻辑不一致，`confirmed_team_id` 被静默忽略

- **位置**：`scripts/providers-map-teams.mjs:78–86`、`157–162`、`179–224`；现行操作说明 `docs/OFFSEASON_OPERATIONS_CHECKLIST__v1.0.md:60`。
- **触发场景**：在 `provider_teams[]` 中使用已支持的 `confirmed_team_id` 指定本地球队，没有再重复填写 `confirmed_mappings[]`；本地球队真实存在，联赛一致。
- **实际行为与根因**：`analyzeTeamMappings()` 同时识别 `confirmed_mappings` 与 `confirmed_team_id`，报告 `confirmed=1`。`applyTeamMappings()` 却只遍历 `confirmed_mappings[]`，返回成功但插入/更新/未变化的映射数量均为 `0`，数据库中仍查不到该映射。运维清单明确将两种形式均描述为可直接 `--apply`。
- **影响**：运营按照只读报告确认后执行应用，升班马的副源映射仍未建立，对应跨源关联及缺映射异常不能按预期收敛。
- **验证证据**：同一有效输入的只读结果为 `confirmed=1`，执行应用后 `mappings_inserted=0`、查询映射为 `null`；对照将该确认记录写入 `confirmed_mappings[]` 后，正常插入 `1` 条并查回目标 `team_id`。执行的是实际脚本导出函数和现有内存仓储。
- **最小修复方向**：只读分析与应用共用同一份已确认映射结果，支持已声明的两种确认形式；保留原有显式冲突处理。
- **最小回归场景**：同一输入先分析再应用，两种确认形式均应得到同样的实际映射结果；无需复杂联调环境。
- **现有测试缺口**：`scripts/providers-map-teams.test.mjs` 的落库用例只使用显式 `confirmed_mappings[]`，没有覆盖 `confirmed_team_id` 从只读到应用的完整流程。

### CR42-04（P2，切片 3）：本周内正常注销会触发周榜名次一致性误报

- **位置**：`src/application/profile-mutation.ts:239–299`；`src/application/daily-consistency-snapshot.ts:588–599`、`914–949`；`src/application/daily-consistency.ts:313–328`；告警写入 `src/application/daily-consistency-service.ts:161–201`。
- **触发场景**：用户本周的一次预测已正常完成结算且有周榜名次，随后在本周结束前注销；之后没有新的结算触发该周重新排名，每日一致性任务先于周末封板运行。
- **实际行为与根因**：注销修改用户身份、冻结赛季等级、退出群组等，但没有重排受影响周榜。校验快照按 `deleted_at < weekEndAt` 将注销用户排除在期望名次之外；在没有活跃结算的情况下，比较函数仍检查实际缓存的 `global_rank`。因此一个正常注销动作会把原本一致的缓存变成确定的告警差异。
- **影响**：每日一致性任务持续报告并持久化非阻塞 `DAILY_CONSISTENCY_MISMATCH`；运营会将正常注销误认为排行榜缓存损坏。后续结算重排或周末封板可以收敛该差异，但本周内的正常注销流程没有闭环。
- **验证证据**：使用实际 `FirstSettlementService` 与原子 item worker 完成一次预测结算，校验结果为空；调用实际 `ProfileMutationService.deleteMyProfile()` 后再加载一致性快照，唯一差异为 `actual.global_rank=1`、`expected.global_rank=null`。继续执行实际 `DailyConsistencyService.run()`，读回一条 `open` 的持久化误报告警。全部在现有内存仓储执行。
- **最小修复方向**：让注销路径同步完成受影响周榜名次更新，并与结算/封板使用一致锁序；保留正常的一致性校验能力，不以全面跳过当前周 `global_rank` 校验代替修复。
- **最小回归场景**：本周结算 → 注销 → 下一次每日一致性校验；未发生数据损坏时不能产生名次差异，也不能新开该误报告警。
- **与 v4.1 的关系**：`CR-05` 修复的是周末封板时的历史周名次重算。本项是尚未到封板时间的本周正常注销场景，是本次进一步发现，不能以历史周验收通过替代。

### CR42-06（P1，切片 3）：周评估跨周漏算，漏一个评估周即永久落后于账本回放

- **位置**：`src/application/weekly-level-eval.ts:297–299`（只按 `weeklyEvalAsOf(serverNow)` 取当前最近周一次评估）、`:513–523`（以持久化旧等级为基线单次评估，无补算循环）；回放口径 `src/domain/levels.ts:387–401`、`:436–444`；调度入口 `src/runtime/scheduled-jobs.ts:334–346`。
- **触发场景**：某用户上周评估因结算阻塞、任务失败或停机未完成，直到下一个评估周才恢复运行。调度器只按“当前最近的周一”选择是否到期，恢复后只评估当周一次。
- **实际行为与根因**：`run()` 只对当前 `as_of` 评估一次，基数是数据库中持久化的旧等级；而 `replayLevel` 以“首次周评估起每个周一”为事件序列逐周折叠。`LEVEL_MAX_STEP_PER_WEEK = 1`，少执行一次评估就少一次升级机会，且该周窗口事实在下一次评估中已按更宽的累计截面计入，无法自动追平。
- **影响**：用户等级、保级次数与回放结果长期分叉；后续评估沿错误基线继续。每日一致性校验与管理员重建会以回放口径计算，因此还会持续产生等级差异告警，重建时等级跳变。
- **验证证据**：用 `dist` 中未修改的 `buildLevelInputs`、`evaluateLevel`、`replayLevel` 构造同一份账本（三周分别 20/30/40 场精确命中，首次评估 2026-08-10T02:00Z）。按时评估 8/10、8/17、8/24 → **Lv3**；漏掉 8/17 只在 8/24 评估 → **Lv2**；同一账本一周一周回放 → **Lv3**。期间没有新增或修正赛果。日志 `reproduce-weekly-level.log`。
- **最小修复方向**：恢复运行或每次评估时，按 `last_eval_as_of` 到当前 `as_of` 之间的遗漏周逐周补算后，再落到当周；补算与回放使用同一事件序列定义。
- **最小回归场景**：同一账本分别走“按时逐周”和“漏一周后恢复”两条路径，最终等级必须与 `replayLevel` 一致。
- **现有测试缺口**：`src/application/weekly-level-eval.test.ts:379` 只覆盖延迟三小时，`:426` 覆盖按时进行的赛季终评；没有“漏一个周评估后恢复”与逐周回放的对比用例。
- **现场相关性（未定性）**：现有 `football-jobs.service` 的 `weekly_level_eval` 正因 `SPEC_GAP: LEVEL_FIRST_EVAL_AS_OF 未登记` 而整轮失败（见第 3 节），若首评时间长期未登记，等级链路会连续多周不产生评估事件。两者可能同源也可能独立，本次未在生产环境验证，故不合并为同一问题。

### CR42-07（P2，切片 3）：每日对账在 READ COMMITTED 下混读结算前后数据，误报一致性异常

- **位置**：`src/application/daily-consistency-snapshot.ts:724`、`:743`、`:844`（多处独立读取 users/stats/rankings/settlements/items）、`:993`（快照在单个事务内加载）；事务隔离级别见 `src/infrastructure/postgres-document-db.ts:1347` 起（普通 `BEGIN`，即 READ COMMITTED）。
- **触发场景**：每日对账读取用户统计（结算前）之后、读取账本（结算后）之前，另一连接完成一次完整结算提交，且该比赛已变为 `settled`。
- **实际行为与根因**：快照不是一致性快照——同一事务内多次读取在 READ COMMITTED 下各自看到语句级最新提交。此时 `actual` 取结算前缓存、`expected` 由结算后账本计算；由于比赛已是 `settled`，`active_settlements` 跳过机制不生效，差异被当成真实不一致写入告警。
- **影响**：正确账本被记为 `DAILY_CONSISTENCY_MISMATCH`，运营看到假告警；若每日对账与结算时段稳定重叠，可反复出现。
- **验证证据**：**未在 PG 复现**。已核对 PG 事务确无固定快照；内存仓储模拟“用户读取与账本读取之间完成提交”出现 `career_points actual=0 / expected=12` 等 5 个字段差异且 `activeSkipped=0`，紧接着重读同一仓储差异为 0。该结论属静态调用链 + 交错模拟，可信度为“高度可能”，需在真库并发下确认后才可当作已证实缺陷。
- **最小修复方向**：让快照在同一次读取口径下取得（例如事务内使用 `REPEATABLE READ`，或先读账本版本再读缓存并以版本一致性判定）。
- **最小回归场景**：真库两连接，A 加载快照中途 B 完成一笔结算提交；对账结果差异必须为 0。
- **现有测试缺口**：`daily-consistency-snapshot.test.ts:345` 覆盖静态 `settling/correcting`，`:894` 覆盖失败修正已入账；均无“两次读取之间完成提交”的并发用例。

### CR42-08（P2，切片 4）：滞留恢复固定只取最早 10 场，未恢复旧场次长期阻挡后续比赛

- **位置**：`src/application/provider-stale-recovery.ts:31–35`（`limit: STALE_RECOVERY_ROUND_CAP` 后即把候选集合当白名单）；`src/infrastructure/active-window-query.ts:145–150`（`compareActiveWindow` 排序后 `slice(0, limit)`）。
- **触发场景**：开球超过 6 小时仍为 `scheduled/live` 的比赛超过 10 场，且最早的 10 场在上游已无可用数据（长期滞留）。
- **实际行为与根因**：每轮都按开球时间取同一批最早 10 场；`fixturesToItems` 只接纳这 10 个候选 ID，因此即使上游返回第 11 场的合法完场结果也会被过滤掉。候选集合没有轮转、游标或按“上次尝试时间”排序。
- **影响**：后续可恢复比赛得不到更新，需等每日全量同步或人工补；旧季已退出全量探测窗口时滞留可能长期存在。
- **验证证据**：独立审查用 `InMemoryRepository` 建 11 场滞留比赛、注入只返回第 11 场合法 FT 的 client，连续三轮恢复均为 `items_read=0`，第 11 场仍 `scheduled/result_version=0`。主审查者已核对上述两处 limit 与排序代码位置；**未在 PG 重跑**。
- **最小修复方向**：候选选取加入轮转或按最近尝试时间推进，保证滞留项不会永久占满名额。
- **最小回归场景**：11 场滞留 + 仅第 11 场可恢复，连续多轮后第 11 场必须被处理。
- **现有测试缺口**：现有滞留恢复测试未覆盖“候选超过上限且最早项不可恢复”的场景。

### CR42-09（P2，切片 6）：设置页主队选择只用包内静态球队，换季新增升班马无法选为主队

- **位置**：`miniprogram/pages/settings/settings.js:48–55`（`buildRegistryTeams` 只遍历 `TEAM_REGISTRY`）、`:150–159`（`loadTeams` 只用该函数结果）、`:164–170`（搜索也只过滤这份名单）。
- **触发场景**：按 v4.0 `Q-PLAN-2` 让新升班马自动入库并补齐中文名/队徽后，用户在设置里搜索并选择该队。
- **实际行为与根因**：选择器没有任何服务端球队发现路径，只枚举打包进小程序的静态注册表；而服务端已支持新增球队（`src/application/provider-team-sync.ts:198`）并接受任意 active 球队作为主队（`src/application/profile-mutation.ts:210`）。限制只发生在小程序入口。
- **影响**：赛程卡片能显示升班马，但用户无法把它设为主队；“换季零重发”在个人资料链路上没有闭环，仍需改静态表并重新发版。
- **验证证据**：独立审查在 Node VM 中执行真实 `loadTeams`，固定得到 **112 队**，新增球队不在选项内；主审查者已核对三处代码位置。真机未验。
- **最小修复方向**：主队候选改为以服务端球队数据为准（或服务端名单与注册表合并），保留现有展示兜底。
- **最小回归场景**：服务端新增一支包内不存在的 active 球队后，设置页可搜索、可选择并成功保存。
- **现有测试缺口**：`miniprogram/pages/settings/settings.test.mjs:80` 只用静态 registry 验证，甚至断言不加载比赛数据。

### CR42-10（P2，切片 6）：过期会话异步恢复成功后，首页仍停留在游客态

- **位置**：`miniprogram/app.js:13–14`（`onLaunch` 不等待 `restoreAuth()`）；`miniprogram/services/auth.js:168–178`；`miniprogram/pages/matches/matches.js:266–276`（`onShow` 仅在 `initialized && hasShown` 时才重新加载）。
- **触发场景**：老用户携带已过期 `auth_session` 冷启动，首页赛程请求先于 `wx.login` 恢复完成发出。
- **实际行为与根因**：公开赛程使用 optional auth，恢复未完成时按匿名请求发出，服务端返回 `AUTH_REQUIRED` 的可预测状态（`src/application/match-query.ts:358–362`），首页据此隐藏预测入口；恢复成功后只写入 token，既不通知首页刷新，`loginGeneration` 也不变化，首次 `onShow` 又跳过重载。
- **影响**：用户看不到预测入口和自己已提交的预测，必须手动切页或重进才恢复。
- **验证证据**：独立审查用 require shim 复现：恢复前 `showPredict=false / reason=AUTH_REQUIRED / listCalls=1`；恢复后 token 已更新为 `renewed`，页面状态与请求次数完全不变。主审查者已核对 `onShow` 条件与 `onLaunch` 未 await 两处代码；真机未验。
- **最小修复方向**：恢复成功后触发一次首页重载（或让 optional 请求等待启动恢复完成）。
- **最小回归场景**：过期会话冷启动 → 自动恢复成功 → 首页预测入口与已有预测无需手动操作即出现。
- **现有测试缺口**：`miniprogram/services/auth.test.mjs:266`、`:289` 只覆盖“公开请求匿名直发”和“私有请求等待恢复”，未覆盖“匿名结果已渲染后恢复成功”的刷新。

### CR42-11（P2，切片 6）：提交请求在途时可继续修改同一份 draft，导致展示比分与服务端保存不一致

- **位置**：`miniprogram/pages/matches/matches.js:588–596`（`onScoreTap` 没有 `submitting` 守卫，直接改 `this.drafts[key]` 同一对象）、`:605`（`onSubmitTap` 取的是对象引用）、`:619–624`（请求体在此刻取数值）、`:641`（成功回调把**当前** draft 铺开写入 `submittedMap`）。
